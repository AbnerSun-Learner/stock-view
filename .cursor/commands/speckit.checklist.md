## 清单宗旨："Unit Tests for English"

**核心理念**：清单是“需求的单元测试”，用于验证需求文本的质量、清晰度与完整性，而非验证实现。

**不用于验证实现/功能**：
- ❌ 不是“验证按钮可点击”
- ❌ 不是“测试错误处理工作正常”
- ❌ 不是“确认 API 返回 200”
- ❌ 不检查代码/实现是否符合规格

**用于验证需求质量**：
- ✅ “是否为所有卡片类型定义了视觉层级要求？”（完整性）
- ✅ “‘突出显示’是否量化了尺寸/位置？”（清晰度）
- ✅ “交互元素的悬停状态要求是否一致？”（一致性）
- ✅ “是否为键盘导航定义了无障碍要求？”（覆盖）
- ✅ “logo 加载失败时的行为是否定义？”（边界）

**比喻**：若规格是英语写的代码，清单就是它的单测，测试的是需求写得是否好，而不是实现是否正确。

## 用户输入

```text
$ARGUMENTS
```

在继续之前必须考虑用户输入（若非空）。

## 执行步骤

1. **初始化**：在仓库根运行 `.specify/scripts/bash/check-prerequisites.sh --json`，解析 FEATURE_DIR 与 AVAILABLE_DOCS（绝对路径）。单引号用 'I'\''m Groot' 方式转义或改用双引号。

2. **动态澄清（最多 3 个初始问题）**：
   - 基于用户描述 + spec/plan/tasks 信号生成精准问题，仅问会实质影响清单内容的信息；已明确则跳过。
   - 问题可含选项表（列 Option/Candidate/Why），选项不超过 A–E；无必要则用简答。
   - 默认（若无法互动）：深度=Standard；受众=Reviewer（代码相关）否则 Author；聚焦前 2 个最高相关领域。
   - 若回答后仍有 ≥2 个场景类（备用/异常/恢复/非功能）不清晰，可再追问最多 2 个（总 ≤5），并给出简短理由。

3. **理解需求**：合并 `$ARGUMENTS` 与澄清答案，提取清单主题、必含项、关注领域与受众/阶段。

4. **加载特性上下文**：
   - 读取 FEATURE_DIR 下 spec.md；如有 plan.md、tasks.md 则提取与关注领域相关的必要片段（渐进式，避免全文）。

5. **生成清单** —— “需求的单测”：
   - 若缺少目录则创建 `FEATURE_DIR/checklists/`。
   - 生成短描述型文件名（如 ux.md、api.md、security.md）；已存在则追加，不覆盖。
   - CHK 编号全局递增（CHK001 起）。
   - 每条聚焦需求质量维度：完整性/清晰度/一致性/可测性/覆盖/边界/非功能/依赖与假设/歧义与冲突。
   - 项目结构参考 `.specify/templates/checklist-template.md`（或使用 H1 标题 + 元信息 + 分类 + `- [ ] CHK### ...`）。
   - 至少 80% 条目需含可追溯引用：`[Spec §X.Y]` 或标记 `[Gap]/[Ambiguity]/[Conflict]/[Assumption]`。
   - 绝对禁止实现级措辞（Verify/Test/Confirm/Click/...）。

6. **输出**：给出清单路径、条目数，并总结：关注领域、深度、受众/阶段、已纳入的用户必需项。提醒每次运行会创建（或追加）新的清单文件。

## 反例 vs 正例
- 错误（测试实现）：`Verify landing page displays...` / `Test hover states...`
- 正确（测试需求）：`是否明确指定精选卡片数量/布局？`、`悬停状态要求是否一致？`、`导航要求是否清晰？`、`相关项选择标准是否定义？`、`加载状态是否定义？`、`“视觉层级”能否量化？`
