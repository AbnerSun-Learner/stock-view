## 用户输入

```text
$ARGUMENTS
```

在继续之前必须考虑用户输入（若非空）。

## 目标
在实施 `/speckit.plan` 之前，发现并减少当前特性规格中的歧义或缺失，并将答案写回规格。

## 执行步骤

1. 在仓库根运行 `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`（仅一次），解析：
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - 可选捕获 `IMPL_PLAN`、`TASKS`
   - 解析失败则中止并提示先运行 `/speckit.specify`。
   - 单引号用 'I'\''m Groot' 方式转义或改用双引号。

2. 加载规格，按下列分类做覆盖扫描，标记 Clear/Partial/Missing（不直接输出原始映射）：
   - 功能范围：核心目标/成功标准、明确不在范围、角色区分
   - 领域与数据：实体/属性/关系、唯一性、生命周期、规模假设
   - 交互与 UX：关键旅程、错误/空/加载、a11y/本地化
   - 非功能：性能、扩展、可靠性、可观测性、安全/隐私、合规
   - 集成与外部依赖：外部服务与失效模式、数据格式、协议/版本假设
   - 边界与异常：负向场景、限流、并发冲突
   - 约束与权衡：技术约束、取舍/备选
   - 术语一致性：术语/禁用同义词
   - 完成信号：可测试的验收/DoD
   - 其他：TODO/占位符/模糊形容词

3. 生成最高优先级的澄清问题队列（最多 5，且全局不超过 10）：
   - 仅选择会实质影响架构/数据/任务分解/测试/UX/运营/合规的问题。
   - 问题必须可用“多选”或“<=5 词短答”回答。
   - 按影响×不确定性排序，覆盖高影响分类；跳过低影响重复。

4. 交互式提问循环（一次只问 1 个）：
   - 多选：先给出**推荐选项**（加粗，1-2 句理由），然后输出表格：

     | Option | Description |
     |--------|-------------|
     | A | ... |
     | B | ... |
     | C | ... |
     | Short | 自定义简答 (<=5 词) |

     末尾提示可回复选项字母/“yes/recommended”。
   - 短答：给出 **Suggested** 答案（含简理由），提示格式为 <=5 词，可回复 yes/suggested 接受。
   - 用户答复后校验；如含糊则追问澄清（不计新增问题）。
   - 满足以下任一即停止：关键歧义清除、用户结束、已问 5 题。
   - 若无高价值问题，直接报告“无关键歧义”。

5. **逐次写入规格**（每获答案立即写）：
   - 首次写入时确保存在 `## Clarifications`，并添加 `### Session YYYY-MM-DD`。
   - 追加条目：`- Q: <问题> → A: <答案>`。
   - 将澄清应用到最合适的章节：
     - 功能 → 功能需求
     - 交互/角色 → 用户故事/角色
     - 数据 → 数据模型
     - 非功能 → NFR/质量属性（量化）
     - 边界/错误 → 边界或异常处理
     - 术语 → 统一命名
   - 若新答案使旧表述失效，替换旧内容，避免矛盾。
   - 每次写入后保存；保持结构与标题不变，新增标题仅限 `## Clarifications` 与对应日期子标题。

6. 每次写入后的校验：
   - 会话内问题 ≤5，Clarifications 列表与答案一致。
   - 相关占位/模糊语被清理，无矛盾表述。
   - Markdown 结构有效，术语一致。

7. 写回 `FEATURE_SPEC`。

8. 汇报：问题数量、规格路径、修改章节、覆盖摘要表（分类状态：Resolved/Deferred/Clear/Outstanding），未解项建议后续动作与下一步命令。

行为准则：
- 不修改文件以外的任何内容；无问题则输出简短“无关键歧义”报告。
- 遵守上限：总问答 ≤5；澄清重试不计新问题。
- 遇到缺失规格文件，提示先运行 `/speckit.specify`。
- 尊重用户停止信号。
